# コミットガイドライン

## コミット単位

- 1コミット = 1つの論理的変更。複数の関心事を1コミットに混ぜない
- 機能変更とリファクタリングは必ず別コミットにする
- すべてのコミットでビルドとテストが通る状態を維持する（壊れた中間状態を作らない）
- タスク完了時に一括コミットせず、作業の途中でも論理的なまとまりごとにコミットする

### 分割の目安

| 変更の種類       | コミット粒度                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| 機能追加         | 1ユースケース / 1エンドポイント単位。大きい場合はドメイン層 → アプリケーション層 → アダプター層の順に分割 |
| リファクタリング | リネーム、メソッド抽出、依存関係の変更などを個別に                                                        |
| バグ修正         | 1バグ1コミット。失敗テスト追加と修正を分けてもよい                                                        |
| 設定・インフラ   | 依存追加、CI変更、Docker変更などはそれぞれ独立                                                            |
| テスト追加       | 既存コードへのテスト補充は、テスト対象の機能単位でまとめる                                                |

## コミットメッセージ

Conventional Commits に従う。日本語で記述する。

```
<type>: <簡潔な説明>
```

### type 一覧

- `feat`: 新機能
- `fix`: バグ修正
- `refactor`: リファクタリング（振る舞いの変更なし）
- `test`: テストの追加・修正
- `docs`: ドキュメントのみの変更
- `chore`: ビルド設定、依存更新など
- `style`: フォーマット変更（コードの意味に影響しない）

### メッセージの書き方

- 1行目は50文字以内を目安に、何を変えたかを簡潔に書く
- 必要に応じて空行の後に補足説明を追加する
- 「なぜ」その変更をしたかが自明でない場合は本文で理由を書く

### 例

```
feat: ユーザー登録APIを追加

POST /api/users エンドポイントを実装。
バリデーションとドメインイベント発行を含む。
```

```
refactor: UserRepository をインターフェースと実装に分離

ドメイン層からインフラ層への依存を除去するため、
依存性逆転の原則を適用。
```

```
fix: ログイン時にセッションが二重生成される問題を修正
```
