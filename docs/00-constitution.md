# Project Constitution

このリポジトリ（個人向け支出記録・分析 Web アプリ、`backend/` + `frontend/` モノレポ）における **不変の原則**。

技術スタック・コマンド・各レイヤー固有のルールは `AGENTS.md` および各サブディレクトリの `AGENTS.md` を参照する。本ファイルはアーキテクチャ判断の前提となる原則を定義する。

## Development Philosophy

### Before Implementation

新しい機能を実装する前に、必ず以下を確認する。

1. 既存のコードベース内に同様の実装やユーティリティがないか検索する
2. 使用しているライブラリ/フレームワークに該当する API や機能がないか確認する
3. Context7 MCP（`mcp__context7__`）を使ってライブラリのドキュメントを参照する

「自分で実装する」より「既存の解決策を使う」を優先する。

### Test-Driven Development (TDD)

機能実装は以下のサイクルで進める。

1. **テスト作成** — 期待する振る舞いに基づきテストを書く。実装コードには触れない
2. **Red 確認** — テストを実行し、期待通りの理由で失敗することを確認する
3. **コミット** — 失敗するテストをコミットする
4. **実装** — テストをパスさせる最小限のコードを書く。テストは変更しない
5. **Green 確認** — すべてのテストが通過するまで実装を修正する
6. **リファクタリング** — テストが通る状態を維持しながら、実装を整理する（必要な場合のみ）
7. **コミット** — 実装（とリファクタリング）をコミットする

テストと実装を同一コミットにまとめない。テスト→実装の順でコミット履歴を残す。

レイヤー別のテスト規約は `backend/AGENTS.md` / `frontend/AGENTS.md` の「テスト方針」セクションを参照する。

## 設計の心得

前提：DDD + レイヤードアーキテクチャ（プロジェクト固有のルールは `backend/AGENTS.md` / `frontend/AGENTS.md` を参照）。

### ドメインモデル

- データだけのモデル（貧血ドメイン）を避け、振る舞いをエンティティ自身に持たせる
- プリミティブ型の素通しを避け、値オブジェクトでドメイン概念を型として守る
- Aggregate 間の参照は ID のみ。トランザクション境界は Aggregate 単位
- 命名はユビキタス言語から取る。`Manager` / `Handler` / `Util` は禁止

### クラス・モジュール

- 責務は一つ。「〜と〜を行うクラス」が浮かんだら分割を疑う
- インターフェースは利用側の都合で切る。提供側の構造に引きずられない
- 具体クラスに直接依存しない。差し替えとテストを常に意識する
- 将来への過剰な汎化を戒める。同じコードが3回現れてから共通化する

### API・インターフェース

- ドメイン内部構造（テーブル名・クラス名）を API に露出しない
- `Request DTO → Command → Domain → Response DTO` の変換を明示的に行う
- ビジネスルール違反は汎用例外で隠さず、専用の例外型で明示する

### データモデル

- テーブル設計の都合でドメインモデルを歪めない。ドメインが先
- 公開する ID と内部の DB 連番を一致させない
- 論理削除を採用する場合、削除済みの除外は Repository の責務として隠蔽する

### 迷ったときの5つの問い

1. この変更理由は一つか？ → 複数なら分割
2. 依存はドメインに向いているか？ → 外向きなら逆転
3. 名前はドメインエキスパートに通じるか？ → 通じないなら命名を見直す
4. 副作用なしに単体テストを書けるか？ → 書けないなら設計を疑う
5. なぜその設計にしたかを一言で言えるか？ → 言えないなら再考する

## Conventions

### 言語

- コード（識別子・メソッド名等）は英語
- コメント・Javadoc・ドキュメントは日本語可

### ブランチ戦略: GitHub Flow

- `main` は常にデプロイ可能な状態を維持する
- `main` から feature/hotfix ブランチを切り、PR でマージする

ブランチ命名:

- 機能追加: `feature/<説明>`（例: `feature/add-expense-api`）
- バグ修正: `hotfix/<説明>`（例: `hotfix/fix-date-validation`）
- 英語・ケバブケースで記述する

### コミット規約

- Conventional Commits 形式で**日本語**で記述する
- 形式: `type(scope): 概要`
- type は `feat / fix / refactor / test / docs / chore / style` のみ使用する
- 1 コミット = 1 つの論理的変更
- 詳細手順は `.claude/skills/commit/SKILL.md` に従う

### AI 由来の明記

AI エージェントが生成した内容は、AI 由来であることを明示する。

- **コミット**: メッセージ末尾に `Co-Authored-By: Claude <noreply@anthropic.com>`
- **PR 本文**: フッターに `🤖 Generated with [Claude Code](https://claude.com/claude-code)`
- **PR レビューコメント / Issue コメント**: 末尾に `🤖 Generated with [Claude Code](https://claude.com/claude-code)`
- 適用範囲は AI が直接生成・送信する内容に限る（人間がレビューして書き換えた場合を除く）

### アーキテクチャ決定（ADR）

- 重要な設計・技術選定は `docs/04-decisions/ADR-NNN-<title>.md` に記録する
- 形式: MADR ライト版（Status / Context / Decision / Consequences）
- ステータス: `Proposed` → `Accepted` / `Rejected` / `Superseded by ADR-NNN`
- 重要な決定があった場合は、ユーザーに ADR への記録を促す
