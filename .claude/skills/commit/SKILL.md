以下のコミットガイドラインに従い、現在のステージ済み・未ステージの変更をコミットしてください。

## 手順

1. `git status` と `git diff`（ステージ済み + 未ステージ）を確認する
2. `git log --oneline -5` で直近のコミットメッセージを確認する
3. 変更内容を分析し、以下のルールに従ってコミットを作成する

## コミット単位のルール

- 1コミット = 1つの論理的変更。複数の関心事を1コミットに混ぜない
- 機能変更とリファクタリングは必ず別コミットにする
- すべてのコミットでビルドとテストが通る状態を維持する
- 変更が複数の論理的なまとまりに分かれる場合は、分割してコミットする

### 分割の目安

| 変更の種類 | コミット粒度 |
|---|---|
| 機能追加 | 1ユースケース / 1エンドポイント単位。大きい場合はドメイン層→アプリケーション層→アダプター層の順に分割 |
| リファクタリング | リネーム、メソッド抽出、依存関係の変更などを個別に |
| バグ修正 | 1バグ1コミット。失敗テスト追加と修正を分けてもよい |
| 設定・インフラ | 依存追加、CI変更、Docker変更などはそれぞれ独立 |
| テスト追加 | テスト対象の機能単位でまとめる |

## コミットメッセージのルール

- Conventional Commits に従い、**日本語**で記述する
- `git commit -m "タイトル" -m "本文"` の形式を使う
- trailer も `-m` で追加する
- 1行目は50文字以内を目安に、何を変えたかを簡潔に書く
- 「なぜ」その変更をしたかが自明でない場合は本文で理由を書く

### type 一覧

- `feat`: 新機能
- `fix`: バグ修正
- `refactor`: リファクタリング（振る舞いの変更なし）
- `test`: テストの追加・修正
- `docs`: ドキュメントのみの変更
- `chore`: ビルド設定、依存更新など
- `style`: フォーマット変更（コードの意味に影響しない）

## 注意事項

- `.env` やクレデンシャルを含むファイルはコミットしない
- 現在のブランチが `main` の場合、先にブランチを切るようユーザーに確認する
- Claude が作成したコミットには trailer を付与する:
  `Co-Authored-By: Claude <noreply@anthropic.com>`
